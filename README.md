# ON AIR — 울산과학고 아침 기상곡 신청 시스템

방송부 이름: on air / 제작: layout

## 아키텍처

- **프론트+백엔드**: Next.js 14 (App Router). 학생 페이지(`/`)와 방송부 페이지(`/admin`)가 같은 프로젝트 안에서 경로만 분리됩니다.
- **DB**: Supabase (Postgres, 무료 티어로 충분)
- **호스팅**: Vercel (무료 티어, 전교생 트래픽 감당 가능)
- **곡 검색/메타데이터/미리듣기**: iTunes Search API + Deezer Search API를 병행 검색 (둘 다 인증·앱 심사·사용자 수 제한이 전혀 없는 공개 API, 30초 미리듣기 URL을 응답에 직접 포함)
- **비속어 2차 체크**: iTunes `trackExplicitness`/`collectionExplicitness` 필드, Deezer `explicit_lyrics` 필드 + Musixmatch 무료 `explicit` 플래그 + 자체 곡명/아티스트명 키워드 사전

> ⚠️ **중요한 한계**: iTunes(애플뮤직) 한국 스토어(`country=KR`) 카탈로그는 국내 유통사가 심의를 거쳐 등록한 버전을 노출하는 경우가 많아, 해외에서는 explicit로 표시된 곡이 국내 스토어에서는 explicit 마킹 없이 올라와 있는 경우가 흔합니다. Deezer도 마찬가지로 지역/유통사에 따라 explicit 마킹이 다르게 붙을 수 있습니다. 즉 **"19" 배지가 하나도 안 뜬다고 해서 그 곡에 정말 부적절한 내용이 없다는 보장은 아닙니다.** 이 체크들은 참고용 1차 필터일 뿐이고, 최종 판단은 방송부가 `/admin`에서 미리듣기를 직접 들어보고 내리는 것을 전제로 설계되어 있습니다. 자체 비속어 사전에 자주 문제 되는 곡/아티스트명을 꾸준히 추가해 두는 것이 가장 실질적인 보완책입니다.

가사 원문 자체는 저작권 문제로 어디에도 저장하지 않습니다. `explicit` 플래그(참/거짓)만 가져와 사용합니다.

### 왜 Spotify가 아니라 iTunes + Deezer 조합인가

처음에는 Spotify Web API로 검색을, YouTube로 미리듣기를 구현하려 했지만 두 가지 문제가 확인됐습니다.

1. Spotify Web API의 신규 앱은 2026년 2월부터 "Development Mode" 제한이 강화되어 **개발자 본인의 Premium 계정 필요 + 앱 사용 가능 인원 최대 5명**으로 제한됩니다. 전교생 규모로 사용하려면 "Extended Quota Mode"가 필요한데, 이제 개인 개발자는 신청 자체가 막혀 있고 정식 법인 + 월간 활성 사용자 25만 명 이상 등 사실상 대기업만 통과 가능한 기준입니다. 즉 API 호출 자체는 무료지만, 학교 프로젝트로 5명 넘는 사용자에게 배포할 방법이 없습니다.
2. Spotify의 30초 미리듣기(`preview_url`)는 2024년 11월부터 신규 앱에 사실상 제공되지 않습니다.

iTunes Search API와 Deezer Search API는 둘 다 인증도, 앱 심사도, 사용자 수 제한도 없는 완전히 공개된 API라 이 문제들을 전부 피할 수 있습니다. 대신 각각 낮은 레이트 리밋(iTunes는 IP당 분당 약 20회, Deezer는 초당 약 10회)이 있어, 두 소스를 병행 검색하면 한쪽 카탈로그에 없는 곡을 다른 쪽에서 찾을 수 있을 뿐 아니라, 합산 호출 한도 자체도 넉넉해집니다.

### 검색 결과 병합과 중복 제거

학생이 검색하면 서버가 iTunes와 Deezer를 **동시에(병렬로)** 호출합니다 (`lib/search.js`). 두 서비스는 트랙 ID 체계가 서로 달라 ID로는 같은 곡인지 판단할 수 없으므로, **곡 제목 + 아티스트명을 정규화한 문자열**을 기준으로 동일 곡 여부를 판단합니다. 정규화 과정에서 대소문자, 공백, 문장부호를 제거하고 괄호 안 내용(예: `(feat. ...)`, `(Remastered)`)도 무시해서, 표기 차이로 인한 오탐을 줄였습니다. 같은 곡이 양쪽에 모두 있으면 iTunes 쪽 결과(이미 검증된 explicit 판정 로직)를 우선 사용하고 Deezer 결과는 버립니다.

#### 노래방·MR 클론 걸러내기

iTunes KR 카탈로그에는 원곡 말고 노래방 반주, MR, 피아노/오르골 커버가 잔뜩 올라와 있고 검색 상위권을 그대로 차지합니다. 실제로 확인해 보면 `아무노래` 검색 상위 10개 중 **6개**가 플로우뮤직 피아노버전·국악버전·모두의MR 같은 클론이었고, `Aqua Man`은 **1위가 금영노래방**이었습니다. 학생이 신청할 수 있는 건 원곡이므로 이런 항목이 자리를 차지하면 정작 찾는 곡이 밀려납니다. 아티스트명(금영노래방, 모두의MR 등)과 명확한 제목 표기(`(MR)`, `[피아노]`, `Karaoke` 등)를 기준으로 걸러냅니다. 정상 곡을 지워버리는 게 더 나쁘므로 판단은 보수적으로 합니다.

#### 두 소스를 섞는 순서 (국내 힙합 검색과 직결)

예전에는 `iTunes 전부 → Deezer 전부` 순서로 이어붙였습니다. 그런데 **iTunes KR에 없고 Deezer에만 있는 곡이 정확히 국내 힙합**입니다(예: 빈지노 `Aqua Man`). 이 방식에서는 그런 곡이 항상 iTunes 결과 전부보다 뒤로 밀리고, 소스별 개수를 늘릴수록 오히려 더 깊이 묻혔습니다.

그래서 **iTunes 2개당 Deezer 1개** 비율로 섞습니다. 1:1로 번갈아 넣으면 흔한 K-pop 검색에서 두 번째 줄마다 엉뚱한 곡이 끼어듭니다(Deezer는 한국어 검색어 관련도가 iTunes보다 눈에 띄게 나쁩니다 — `newjeans`의 Deezer 2번째 결과가 League of Legends의 `GODS`). 2:1이면 상단은 깨끗하게 유지되면서 Deezer 전용곡도 첫 화면(10개) 안에 들어옵니다.

#### 소스별 개수와 "더보기"

각 소스에서 **50개씩** 받아옵니다. iTunes/Deezer 모두 `limit`과 무관하게 **호출 1회**라서, 이 값을 올려도 레이트 리밋 소모량은 똑같습니다. 걸러내고 섞어서 최대 40곡을 내려보내고, 화면에는 10개만 보여준 뒤 **"더보기"로 10개씩 펼칩니다.** 더보기는 이미 받아온 결과를 펼치는 것뿐이라 API를 다시 호출하지 않습니다.

> **여전히 코드로 못 고치는 것**: `롤러코스터`(칠린호미), `Ghost`(저스디스)처럼 흔한 제목은 200위까지 봐도 더 유명한 아티스트 곡에 묻혀 안 나옵니다. 아예 iTunes KR 카탈로그에 없는 곡도 있습니다. 이런 경우는 **아티스트명으로 검색**하거나(예: `밖에 비와`는 제목으로는 안 나오지만 `래원`으로 검색하면 10위 안에 나옵니다) **"곡명으로 직접 신청하기"** 를 쓰면 됩니다.

### API 레이트 리밋 대비책

전교생이 아침 시간대에 몰리면 각 API의 분당/초당 한도를 쉽게 넘길 수 있어, iTunes와 Deezer 각각에 동일한 세 가지 장치를 코드에 넣었습니다.

1. **검색 결과 캐싱** (`itunes_search_cache`, `deezer_search_cache` 테이블): 같은 검색어는 12시간 동안 해당 API를 다시 호출하지 않고 캐시에서 응답합니다. 인기곡은 검색어가 겹치는 경우가 많아 실제 호출 수가 크게 줄어듭니다.
2. **자체 호출 카운터** (`itunes_call_log`, `deezer_call_log` 테이블): iTunes는 최근 1분간 호출 수가 18회(한도 20회)에, Deezer는 최근 10초간 호출 수가 40회(한도 40~50회 수준)에 도달하면 해당 API를 아예 호출하지 않고 다른 소스 결과만으로 응답합니다. 두 소스가 동시에 한도에 걸렸을 때만 "검색 요청이 몰려 있다"는 안내를 보여줍니다. 이 로그는 최근 1분/10초치만 의미가 있어서, 가끔씩 1시간 지난 행을 자동으로 정리합니다.
3. **429 폴백**: 혹시 어느 한쪽 API가 429를 반환해도 서버가 죽지 않고, 다른 소스의 결과만이라도 정상적으로 보여줍니다. 한쪽만 막혔는데 살아있는 쪽이 마침 0건을 준 경우에는 "지금 곡 정보를 절반만 불러올 수 있는 상태"라고 따로 알려줍니다 — 이걸 그냥 두면 학생이 "그런 곡이 없구나"로 오해하는데 실제로는 검색이 반쪽이었던 상황이기 때문입니다.

한도에 걸렸을 때 대기시키거나 줄을 세우지 않고 **즉시 다른 소스 결과만 반환**하는 구조라, 요청이 몰려도 응답이 느려지지는 않습니다. 대신 그 시간대에는 **검색 품질이 떨어집니다**(Deezer는 국내곡 커버리지가 얇습니다). 즉 부하의 증상은 "렉"이 아니라 "국내곡이 잘 안 잡힘"으로 나타납니다.

이 구조 덕분에 한쪽 API가 완전히 막혀도 다른 쪽으로 검색이 계속되고, 두 소스를 합친 만큼 실질적인 검색 처리량도 늘어납니다. 캐시 TTL이나 각 레이트 리밋 값은 `lib/itunes.js`, `lib/deezer.js`에서 조정할 수 있습니다.

### 검색은 DB가 죽어도 계속됩니다

위 캐시와 카운터는 **검색을 빠르게 하려는 보조 장치**일 뿐, 검색 자체에 꼭 필요한 건 아닙니다. 그래서 Supabase가 잠깐 느려지거나 응답하지 않아도 검색은 캐시 없이 iTunes/Deezer를 직접 호출해서 정상적으로 결과를 돌려줍니다. 외부 API 호출(5초)과 DB 호출(3초)에는 각각 타임아웃이 걸려 있어, 어딘가 응답이 없어도 학생 화면이 "검색 중…"에서 무한정 멈추지 않습니다.

마찬가지로 방송부 로그인도 DB를 거치지 않는 별도 엔드포인트(`/api/admin/verify`)로 확인하기 때문에, DB 문제 때문에 비밀번호가 틀린 것처럼 보이는 일이 없습니다. DB 조회가 실패하면 대시보드 안에 빨간 오류 문구로 표시됩니다 — 신청이 0건인 것처럼 조용히 비어 보이지 않습니다.

## 배포 순서

### 1. Supabase 프로젝트 만들기
1. [supabase.com](https://supabase.com) 에서 새 프로젝트 생성
2. SQL Editor에서 `supabase_schema.sql` 파일 내용을 그대로 실행
3. Project Settings > API 에서 `Project URL`과 `service_role` 키(anon 키 아님, secret 키)를 복사

> **이미 이전 버전을 배포해서 DB를 만들어 둔 경우**: `supabase_schema.sql`을 처음부터 다시 실행할 필요 없이, 아직 실행하지 않은 마이그레이션 파일만 SQL Editor에서 추가로 실행하면 됩니다.
> - "곡 직접 등록" 기능이 없다면 → `supabase_migration_manual_songs.sql` 실행
> - Deezer 병행 검색 기능이 없다면 → `supabase_migration_deezer.sql` 실행
> - **중복 신청 방지 인덱스가 없다면 → `supabase_migration_dedup.sql` 실행** (아래 설명 참고)
> 세 파일 모두 이미 반영된 부분은 건드리지 않고 없는 부분만 추가하도록 만들어져 있어, 여러 번 실행해도 안전합니다.

> **`supabase_migration_dedup.sql`은 실행을 권장합니다.** 중복 신청 방지가 그동안 "먼저 조회해 보고 없으면 저장" 방식이라, 같은 학생이 아주 짧은 간격으로 두 번 신청하면(버튼 연타, 모바일 더블탭 등) 두 요청이 동시에 조회를 통과해 둘 다 저장될 수 있었습니다. 이 마이그레이션은 DB에 unique index를 걸어 그런 경우까지 확실히 막습니다. 이미 중복 데이터가 쌓여 있으면 인덱스 생성이 실패하는데, 그때는 파일 맨 아래 주석의 조회 쿼리로 중복을 먼저 확인하고 정리한 뒤 다시 실행하면 됩니다.

### 2-1. 결과 안내 메일 설정 (선택)

승인/반려/방송일 배정이 되면 학생 학교 메일(`{앞자리}@ushs.hs.kr`)로 결과가 자동 발송됩니다. 설정하지 않으면 **메일 기능만 조용히 꺼지고 나머지는 그대로 동작**합니다.

1. [resend.com](https://resend.com) 무료 가입 → API 키 발급 → `RESEND_API_KEY`
2. Resend에서 **보내는 도메인을 등록하고 DNS 인증**까지 마친 뒤 `MAIL_FROM`에 그 도메인 주소를 넣습니다 (예: `ON AIR <onair@example.com>`)
   - 도메인 인증 전에는 Resend 가입에 쓴 본인 주소로만 테스트 발송이 됩니다. 학생 메일로 실제로 보내려면 인증이 필수입니다.
3. `APP_URL`에 배포 주소를 넣으면 메일 안의 "내 신청 현황 보기" 버튼이 그 주소를 가리킵니다.

> **무료 티어 한도에 주의하세요.** Resend 무료 플랜은 하루 100통 / 월 3,000통입니다. 그래서 신청 접수 시점에는 메일을 보내지 않고 **결과가 정해졌을 때(승인·반려·방송일 배정)만** 발송합니다. 전교생이 몰리는 날에는 한도를 넘길 수 있으니, 넘겼을 때는 메일만 실패하고 승인/반려 자체는 정상 처리됩니다(실패는 서버 로그에만 남습니다).

메일은 곡 제목·아티스트·앨범아트·상태 배지·방송 예정일·반려 사유가 들어간 HTML로 구성되고, HTML을 못 읽는 환경을 위한 텍스트 본문도 함께 보냅니다. 문안이나 색을 바꾸려면 `lib/mailer.js`의 `TEMPLATES`만 고치면 됩니다.

### 2. Musixmatch API 키 발급 (선택이지만 권장)
1. [developer.musixmatch.com](https://developer.musixmatch.com) 무료 가입
2. API 키 발급 (explicit 플래그 조회 용도로만 사용, 가사 전문은 절대 가져오지 않음)
3. 키를 발급받지 않아도 서비스는 정상 동작합니다 (해당 체크만 건너뜀)

### 3. 환경변수 설정
`.env.example`을 참고해서 Vercel 프로젝트의 Environment Variables에 아래 값을 전부 입력합니다.

> ⚠ **실제 키는 `.env.example`에 적지 마세요.** 이 파일은 항목 이름만 알려주는 예시 파일이고 저장소에 함께 올라갑니다. 진짜 값은 로컬에서는 `.env.local`(`.gitignore`에 포함됨), 배포에서는 Vercel Environment Variables에만 넣습니다. 실수로 키를 커밋했거나 어딘가에 공유했다면, 그 키는 이미 노출된 것으로 보고 Supabase 대시보드에서 새로 발급(rotate)하고 `ADMIN_PASSWORD`도 바꿔야 합니다.

```
SUPABASE_URL
SUPABASE_SERVICE_ROLE_KEY
MUSIXMATCH_API_KEY   <- 선택
ADMIN_PASSWORD       <- 방송부끼리 공유할 비밀번호, 직접 정하기
RESEND_API_KEY       <- 선택 (결과 안내 메일)
MAIL_FROM            <- 선택 (결과 안내 메일, 인증된 도메인 주소)
APP_URL              <- 선택 (메일 버튼이 가리킬 배포 주소)
```

### 4. Vercel 배포
1. 이 폴더를 GitHub 저장소에 올리기
2. [vercel.com](https://vercel.com) 에서 New Project > 해당 저장소 선택
3. 위 환경변수 입력 후 Deploy

배포가 끝나면:
- 학생용 페이지: `https://프로젝트명.vercel.app/`
- 방송부 페이지: `https://프로젝트명.vercel.app/admin` (비밀번호 입력 필요)

두 페이지의 링크를 다르게 안내하면 됩니다 (학생들에게는 `/admin` 경로를 알리지 않으면 됨).

## 학생 사용법

1. `/` 접속 후 이메일 앞자리(`_______@ushs.hs.kr`의 밑줄 부분) 입력
2. **곡 신청** 탭에서 곡명/아티스트로 검색 → 결과에서 "신청하기" 클릭
3. 검색해도 원하는 곡이 안 나오면, 결과 목록 아래 "찾는 곡이 없나요? 곡명으로 직접 신청하기"를 눌러 곡 제목과 아티스트를 직접 입력해 신청할 수 있습니다. 이렇게 신청한 곡도 방송부 검토(승인/반려) 절차를 동일하게 거칩니다.
4. **내 신청 현황** 탭에서 본인이 신청한 곡들의 진행 상태(검토 대기/승인/반려/방송 예정/방송 완료)를 확인할 수 있습니다.
5. **방송 예정곡** 탭에서 전교생에게 공개된, 날짜가 배정된 기상곡 목록을 볼 수 있습니다.
6. 19금(explicit)으로 표시된 곡은 곡명 옆에 빨간 "19" 배지가 붙고 미리듣기가 제공되지 않지만, 신청 자체는 그대로 가능합니다. 최종 방송 여부는 방송부가 결정합니다.
7. **하루에 3곡까지** 신청할 수 있습니다. 검색창 아래에 오늘 몇 곡 더 신청할 수 있는지 표시되고, 다 쓰면 신청 버튼이 "오늘 마감"으로 잠깁니다. 반려된 곡은 한도에서 빠지므로 다시 신청할 수 있습니다. 기준 시각은 한국 시간 자정입니다. 개수는 `lib/dailyQuota.js`의 `DAILY_LIMIT`에서 바꿀 수 있습니다.
8. 승인/반려/방송일이 정해지면 **학교 메일로 결과가 옵니다** (메일 설정을 한 경우).

## 방송부 사용법

1. `/admin` 접속 후 비밀번호 입력
2. 들어가면 **대시보드**가 먼저 뜹니다. 지금 처리해야 할 것들을 한 화면에 모아둔 곳입니다.
   - 맨 위 큰 숫자: **검토 대기 건수** (이 화면에서 제일 먼저 봐야 할 숫자)
   - 그 아래 네 칸: 확인 필요 / 배정 대기 / 방송 예정 / 방송 완료 — **누르면 해당 상태만 걸린 목록 탭으로 바로 이동**합니다
   - **오늘의 기상곡**: 오늘 날짜로 배정된 곡. 여기서 바로 "방송 완료" 처리 가능
   - **다가오는 방송**: 가까운 순서대로 예정된 곡
   - **완료 처리가 안 된 곡**: 방송일이 지났는데 아직 완료 처리를 안 한 곡 (안 치우면 예정 목록에 계속 쌓입니다)
   - **최근 신청**: 검토 대기 중인 최신 신청. 확인 필요 표시가 붙은 곡은 목록 탭에서 미리듣기로 확인한 뒤 판단하고, 문제없는 곡은 여기서 바로 승인할 수 있습니다
3. 상단 탭에서 **대시보드 / 목록 / 달력 / 곡 직접 등록 / 비속어 사전 / 데이터 관리** 중 선택
4. **목록** 탭: 반려할 때는 자주 쓰는 사유를 버튼으로 고를 수 있습니다(고른 뒤 수정 가능). **반려 사유는 학생에게 메일로 그대로 전달되므로** 학생이 읽을 문장으로 씁니다. "검토 대기" 상태에서 신청곡 확인, iTunes 30초 미리듣기로 청취. ⚠ 배지가 뜬 곡은 iTunes/Musixmatch explicit 플래그나 자체 사전에 걸린 경우이니 재생해서 직접 확인 후 승인/반려 결정. **한 번 승인/반려하면 그 버튼은 다시 뜨지 않습니다** — 승인된 곡은 날짜 배정 UI만, 반려/완료된 곡은 상태 표시만 남습니다. 학생이 검색 없이 직접 곡명을 입력해 신청한 경우 카드에 별도 표시는 없지만, 미리듣기가 없을 가능성이 높으니 곡 제목/아티스트를 보고 직접 확인하는 과정이 특히 중요합니다.
5. 승인된 곡은 날짜 선택 후 "이 날짜로 배정"을 누르면 학생들 "방송 예정곡" 탭에 노출됩니다. 배정 후에도 날짜는 다시 바꿀 수 있습니다.
6. 방송 끝난 곡은 "방송 완료 처리" 클릭
7. **달력** 탭: 월별 달력에 그 달 예정/완료된 기상곡이 날짜별로 표시됩니다. 승인된(아직 날짜 미배정) 곡이 있다면 빈 날짜를 클릭해서 바로 배정할 수 있습니다.
8. **비속어 사전** 탭에서 자체 필터링 키워드를 직접 추가/삭제 가능 (곡명·아티스트명 기준)
9. **곡 직접 등록** 탭: iTunes 검색에 안 잡히는 곡(예: 국내 유통 계약 미체결 곡)을 방송부가 직접 곡명/아티스트를 입력해서 등록합니다. 여기서 등록한 곡은 학생 신청 없이 바로 **승인(approved)** 상태로 들어가고, 곧바로 목록/달력 탭에서 날짜 배정이 가능합니다. 앨범아트나 미리듣기 URL은 선택 입력이라 없어도 등록됩니다. 목록에서는 "직접 등록" 배지로 일반 학생 신청곡과 구분됩니다.
10. **데이터 관리** 탭: 방송 완료된 곡만, 반려된 곡만, 또는 전체 신청 데이터를 삭제할 수 있습니다. 실수 방지를 위해 "삭제확인"이라는 문구를 정확히 입력해야만 실행되며, 되돌릴 수 없는 작업이니 신중하게 사용해야 합니다. 비속어 사전 자체는 이 기능으로 지워지지 않습니다.

개별 신청곡도 각 카드 하단의 "이 신청 삭제"로 하나씩 지울 수 있습니다 (2단계 확인 필요).

## 알아두면 좋은 점

- 학생 신원 확인은 이메일 인증이 아니라 `_______@ushs.hs.kr`의 밑줄 부분을 자율적으로 입력받는 방식입니다. 실제 학교 이메일 로그인 연동이 아니므로 완전한 신원 보증은 아니지만, 익명 신청보다 책임소재를 명확히 하는 최소한의 장치입니다. 입력값은 영문/숫자 2~30자만 허용되며, 학생 화면에서도 서버와 같은 규칙으로 미리 검사해서 신청 버튼을 누른 뒤에야 형식 오류를 보는 일이 없게 했습니다.
- "내 신청 현황"은 이메일 앞자리만 알면 누구나 조회할 수 있는 구조라, 응답에는 학생 본인에게 필요한 항목(상태·방송일·반려 사유)만 담고 방송부 내부 정보(어떤 사전 항목에 걸렸는지, 담당자 이름 등)는 내려보내지 않습니다.
- 같은 학생이 같은 곡을 중복 신청하는 것은 서버에서 막아둡니다(대기/승인/예정 상태에 한해). `supabase_migration_dedup.sql`을 실행해 두면 버튼 연타처럼 동시에 들어온 요청까지 DB가 확실히 막아줍니다. 반려되거나 방송이 끝난 곡은 다시 신청할 수 있습니다.
- 한 번 신청한 곡은 검색 결과에서 버튼이 "신청됨"으로 바뀌어 잠깁니다.
- 30초 미리듣기 플레이어는 브라우저 기본 `<audio controls>` 대신 직접 만든 컨트롤(`app/components/AudioPreview.js`)입니다. 기본 플레이어는 크롬에서 흰색 알약 모양이라 어두운 화면에서 곡 정보보다 더 튀었고, 브라우저마다 생김새도 달랐습니다. 진행 바를 눌러 원하는 지점으로 이동할 수 있고(키보드 ←/→로 5초씩), 목록에서 다른 곡을 재생하면 먼저 재생 중이던 곡이 자동으로 멈춥니다.
- 곡명·아티스트·반려 사유 등 글자 수 상한(200자, 사전 키워드는 100자)은 화면과 서버 양쪽에서 같은 값으로 검사합니다. 앨범아트/미리듣기 URL은 `http(s)` 주소만 저장합니다.
- `needs_review`는 DB에서 자동 계산되는 컬럼이라 세 조건 중 하나라도 참이면 자동으로 방송부 화면에 경고가 뜹니다.
- iTunes 검색은 일부 최신곡이나 마이너한 곡이 국내(KR) 스토어 기준으로 안 잡힐 수 있습니다. 국내 스트리밍 서비스에는 있어도 애플뮤직 카탈로그 자체에 유통 계약이 안 되어 있는 경우로, 코드로 해결할 수 있는 문제가 아닙니다. 이 경우 방송부가 곡을 직접 확인해서 예외적으로 처리할 필요가 있을 수 있습니다.
- 학생 페이지에서 19금(explicit) 곡은 검색과 신청은 그대로 가능하지만, 곡명 옆에 빨간 "19" 배지가 붙고 미리듣기 오디오는 제공되지 않습니다. 최종 판단(승인/반려)은 방송부가 `/admin`에서 미리듣기를 들어보고 내립니다.
- 두 페이지 모두 모바일 화면 폭(768px 미만)에서 레이아웃이 세로로 재배치되도록 만들어져 있어 학생들이 휴대폰으로 신청하는 상황을 기준으로 사용성을 맞췄습니다.

## 트러블슈팅

**Vercel 배포 시 `Error: supabaseUrl is required`가 뜨는 경우**

이건 `SUPABASE_URL` 환경변수가 빌드 시점에 비어있었다는 뜻입니다. Vercel 프로젝트 Settings > Environment Variables에 값이 실제로 저장되어 있는지, 이름에 오타가 없는지 확인하고, **환경변수를 추가/수정한 뒤에는 반드시 Deployments 탭에서 최신 배포를 Redeploy** 해야 반영됩니다. 저장만 하고 재배포를 안 하면 이전 빌드에는 값이 반영되지 않습니다.

**Supabase 키를 잘못 넣은 경우**

Supabase가 키 이름을 개편해서 `publishable`(구 anon, 클라이언트 노출용)과 `secret`(구 service_role, 서버 전용) 두 가지로 나뉩니다. 이 프로젝트의 `SUPABASE_SERVICE_ROLE_KEY`에는 **secret** 키(`sb_secret_...` 또는 legacy `eyJ...` 형식)를 넣어야 합니다. `sb_publishable_...`로 시작하는 값을 넣으면 RLS 정책에 막혀 신청 저장/조회/승인이 전부 실패합니다. Supabase 대시보드 Settings > API Keys에서 "Publishable and secret API keys" 탭의 Secret keys, 또는 "Legacy API Keys" 탭의 service_role 값을 사용하세요.
